# Пример: обзор проекта с разных сторон

**Запрос:** «Оцени мой локальный проект: архитектура, безопасность, удобство для пользователей и возможность поддерживать его одному разработчику».

Сначала экспертная панель выясняет, какие файлы доступны и можно ли запускать тесты. Если файлов нет, она не выдумывает находки: просит ссылку или структуру проекта и предлагает критерии будущей проверки. Если файлы доступны, она ограничивает область анализа просмотренными путями.

## Формат результата

**Итог:** Из просмотренных компонентов выявлены проверенные проблемы и непроверенные риски. Рекомендация относится только к перечисленным файлам.

| Ракурс | Вопрос | Проверяемое основание |
|---|---|---|
| Архитектор | Где проходит граница между компонентами? | Конкретные зависимости и точки вызова в файлах |
| Специалист по безопасности | Где недоверенные данные влияют на поведение? | Путь данных, защитные проверки, разрешённый контекст |
| Представитель пользователя | Можно ли выполнить главный сценарий? | Наблюдаемое поведение или предоставленные пользовательские сценарии |
| Сопровождающий | Как вносить и проверять изменения? | Документация, команды, фактически выполненные тесты |
| Аудитор доказательств | Чем подтверждён каждый вывод? | Точные места в коде и результаты проверок |

**Находка F-1:** `[путь:строка]` — наблюдение, последствия, проверка, безопасное исправление, уровень уверенности. Не подменять наблюдение предположением.

**Расхождение:** Улучшение скорости разработки может ухудшить поддержку; решение опирается на приоритеты пользователя, а не на голосование ролей.

**Ограничения:** `[непросмотренные каталоги]`; тесты `[выполнены с результатом / не выполнялись]`; отдельные ролевые проходы одной модели не являются независимыми экспертами.

**Первое действие:** Небольшое обратимое исправление с наблюдаемым критерием успеха. Не публиковать, не развёртывать и не удалять файлы без разрешения.

Это пример структуры отчёта, а не утверждение, что конкретный проект был проверен.
